# Contributing

Thank you for helping improve the AI Development Control Plane program.

## Choose the right channel

- Use a GitHub Discussion for an early idea, question, research result, integration concept, or design conversation.
- Use the structured Work Proposal issue form for one concrete, actionable problem or desired outcome.
- Use private vulnerability reporting for security vulnerabilities.

Public bug observations, research evidence, documentation ideas, provider/device/platform requests, and usability improvements can be raised through Discussions first and converted into a Work Proposal when actionable.

## Before filing a Work Proposal

1. Search existing Discussions and Issues.
2. Describe the problem before prescribing architecture.
3. Keep one primary problem or outcome per issue.
4. Explain affected users or use cases when relevant.
5. Include public-safe evidence and alternatives when available.
6. Identify known resource or cost implications.
7. Do not include confidential or sensitive information.

## Implementation pull requests

The canonical implementation repositories are private. Do not open implementation-code pull requests in this community repository.

External implementation or documentation pull requests are not part of the initial community launch. A public contribution and license model must be selected before external PR contributions are enabled.

## Architecture

Contributions must respect:

**CENTRALIZED AUTHORITY AND TRUTH; DISTRIBUTED CAPABILITIES AND OBSERVATIONS.**

A proposal must not create a second global Authority, Policy Engine, canonical Registry truth, unrestricted host/network/device mutation path, or silently absorb another provider project's responsibility.

## Economic operation

Prefer the smallest sufficient zero-cost solution. Avoid paid dependencies, unnecessary hosted inference, duplicate services, excessive polling, unnecessary always-on processes, and wasteful CPU/GPU/RAM/storage/network/token use.

Economic optimization must not weaken security, privacy, correctness, truthfulness, evidence, reliability, required capability, provider neutrality, or OS neutrality.

## Conduct

Constructive disagreement is welcome. Harassment, spam, threats, personal attacks, or disclosure of private or sensitive data are not acceptable.

## Maintainer decisions

Maintainers may request information, redirect, mark duplicate, close out-of-scope proposals, or defer work. `accepted-for-design` means design evaluation only, not implementation acceptance, priority, merge authorization, or production authorization.
